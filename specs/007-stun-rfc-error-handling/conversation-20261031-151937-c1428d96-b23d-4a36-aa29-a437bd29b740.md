# RFC 5389 / 5769 / 5780 实现检查报告

**结论**：UDP 上的基础 Binding 请求可用，`XOR-MAPPED-ADDRESS` 的 XOR 运算正确；但 README 中"fully compliant with RFC 5389"的说法不成立，RFC 5780 基本没有实现，且存在一个可复现的协议级错误（未知 comprehension-required 属性应返回 420，实际返回成功）。

## 验证方式

- 逐条对照 `docs/rfcs/` 中的条款与 `crates/stun-protocol`、`src/server` 实现
- 实际向服务器发送三类请求，观察响应类型（见下方"证据"）

## P0：违反 MUST / 会造成互通问题

### 1. 未实现 420 (Unknown Attribute)，也没有任何错误响应能力
RFC 5389 §7.3.1（rfc5389.txt:934-938）：请求含未知 comprehension-required 属性（类型 < 0x8000）时，服务器必须返回 420，并附带 `UNKNOWN-ATTRIBUTES`。

当前实现解析后不检查属性类型，直接构造成功响应：
- `src/server/server.rs:140-153` 只判断 `message_type == Request`，属性被完全忽略
- `crates/stun-protocol/src/attributes.rs:29-41` 未识别的类型一律映射为 `Unknown`，但服务器不做任何处理
- 代码中根本没有 `ERROR-CODE`/`UNKNOWN-ATTRIBUTES` 的编码逻辑（`error.rs` 只有解析错误类型）

**证据**（实际运行探测，均返回成功响应）：
```
CHANGE-REQUEST(0x0003)              -> 0x0101 (应为 0x0111 + 420)
unknown PRIORITY(0x0024)            -> 0x0101 (应为 0x0111 + 420)
USERNAME(0x0006)                    -> 0x0101
RFC 5769 §2.1 官方样例请求           -> 0x0101（MI/FINGERPRINT/ICE 属性被静默忽略）
```
RFC 5389 §12.2（rfc5389.txt:1614-1617）也明确指出：不支持 RFC 3489 兼容时，带 `CHANGE-REQUEST` 的请求应被当作未知 comprehension-required 并返回错误响应。当前行为与规范相反。

### 2. RFC 5780 CHANGE-REQUEST 处理缺失
RFC 5780 §6（rfc5780.txt:1022-1024）：服务器没有第二个 IP/端口时，收到 `CHANGE-REQUEST` **必须**返回 420。当前该属性（0x0003）被当作未知属性忽略，返回成功，如上证据。

### 3. RFC 5780 属性码定义错误（`attributes.rs:16-22`）
| 代码中的枚举 | 代码值 | RFC 5780 实际含义 |
|---|---|---|
| `SourceAddress` | 0x802B | **RESPONSE-ORIGIN** |
| `ChangedAddress` | 0x802C | **OTHER-ADDRESS** |
| `OtherAddress` | 0x802D | 未定义（OTHER-ADDRESS 不是 0x802D） |

同时缺失 `CHANGE-REQUEST (0x0003)`、`PADDING (0x0026)`、`RESPONSE-PORT (0x0027)`、`CACHE-TIMEOUT (0x8027)`。`summary.rs:71-82` 会因此把对端的 RESPONSE-ORIGIN/OTHER-ADDRESS 打印成 SOURCE-ADDRESS/CHANGED-ADDRESS，排查日志会误导。目前服务器不发送这些属性，所以暂时只是潜伏缺陷，但一旦做 5780 支持必然出错。

### 4. 不支持 TCP，与 RFC 5389 §13 冲突
RFC 5389 §13（rfc5389.txt:1646-1647）：basic stand-alone server **MUST support UDP and TCP**。当前只绑定 UDP（`server.rs:107`），配置里的 TCP 超时项（`config.rs:207-220`）完全未使用。README 却声称 "fully compliant"（README.md:3,10）。

连带问题：`docker/Dockerfile:47-48` 暴露 TCP 3478，且健康检查 `nc -z localhost 3478`（Dockerfile:54-55）走的是 TCP，容器会永远处于 unhealthy。

## P1：RFC 5780 能力缺失 / SHOULD 项

如果目标是支持 NAT 行为发现，以下都缺：
- 双 IP + 双端口的 socket 设计（rfc5780.txt:989-1000）
- `RESPONSE-ORIGIN`（MUST，rfc5780.txt:1071-1073）
- `OTHER-ADDRESS`（有第二地址时 MUST，rfc5780.txt:1075-1080）
- 响应中同时包含 `MAPPED-ADDRESS` 和 `XOR-MAPPED-ADDRESS`（MUST，rfc5780.txt:1019-1020），当前只有 XOR
- `PADDING` 回显、`RESPONSE-PORT` 发送目标端口、二者同时出现时返回 400（rfc5780.txt:1082-1087）

其他 SHOULD 级问题：
- 成功响应未带 `SOFTWARE`（RFC 5389 §7.3.1.1，SHOULD，rfc5389.txt:1000）
- 未支持 RFC 3489 老客户端兼容（§12.2 SHOULD；magic cookie 不匹配直接丢弃）
- `FINGERPRINT` 未识别/校验——对 standalone 服务器属 MAY，可接受；但若将来与其它协议复用端口，必须校验（§7.3、§8.1）
- `MESSAGE-INTEGRITY` 被忽略——basic server 按 §13 SHOULD NOT 使用凭据机制，可接受；但带 MI 的客户端会收到不带 MI 的响应，无法通过其校验

## P2：测试与工程问题

- **`crates/stun-protocol/tests/rfc5769_vectors.rs` 名不副实**：没有使用 RFC 5769 的真实字节向量（样例 IPv4 端口应为 32853，测试用的是 3478），没有解码官方样例请求/响应，也没有 MI/FINGERPRINT 用例（文件开头自己写的是 "inspired by"）。目前只证明了编解码自洽，不能证明与规范互通。
- `StunMessageType::ErrorIndication`（message.rs:23）命名有误：0x0111 是 **Binding Error Response**，Indication 是 0x0011。
- 解码器容忍 `data.len() > header + length` 的尾部字节（message.rs:167-173），属性长度也允许大于预期长度；宽松但可能掩盖畸形包。
- 每收到一个 UDP 包就 `tokio::spawn`（server.rs:135），无并发上限/限速，存在反射放大与任务爆炸风险。
- 只处理 SIGINT（server.rs:182-186），systemd 停止时发 SIGTERM，会跳过优雅关闭。

## 实现正确的部分

- 头部 20 字节、magic cookie、长度 4 字节对齐、最小长度校验（message.rs:138-181）
- `StunMessageType` 严格匹配，非法/非 Request 消息静默丢弃（符合 §7.3）

- Binding 幂等、无状态重传处理符合 §7.3.1
- 属性编码补齐 4 字节 padding（attributes.rs:70-99）

1. **实现错误响应**：`ERROR-CODE` + `UNKNOWN-ATTRIBUTES` 编码，请求属性扫描（< 0x8000 且未实现 → 420），同时覆盖 CHANGE-REQUEST

`stunclient` 目前**没有**设置 attribute 的参数。它只发送一个不带任何 attribute 的裸 Binding Request：

- CLI 参数只有 `server`、`--timeout`、`--quiet`、`--debug`、`--trace`、`-4/--ipv4-only`、`-6/--ipv6-only`（`src/client/main.rs:25-54`）

```python
import socket, struct, os

txid = os.urandom(12)
attr = struct.pack("!HH", 0x0024, 4) + b"\x00\x00\x00\x01"   # PRIORITY
msg = struct.pack("!HHI", 0x0001, len(attr), 0x2112A442) + txid + attr

s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.settimeout(2)
s.sendto(msg, ("127.0.0.1", 3478))
data, _ = s.recvfrom(65536)
print(data.hex())
```
