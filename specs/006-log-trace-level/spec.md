# Feature Specification: 日志 TRACE 分级与轮转命名优化

**Feature Branch**: `006-log-trace-level`

**Created**: 2026-10-31

**Status**: Draft

**Input**: User description: "日志调整，增加trace日志级别：现有 [DEBUG] Received / [DEBUG] Response 原始报文日志调整为 TRACE 级别；增加 [DEBUG] Received 具体接收消息体内容、[DEBUG] Response 响应消息内容日志输出；命令行增加 --trace 参数开启 trace 日志级别；日志文件轮转增加当天时间.N"

## Clarifications

### Session 2026-10-31

- Q: DEBUG 与 TRACE 两级日志分别应输出什么内容？ → A: DEBUG 输出解析后的可读消息摘要（类型、事务 ID、属性及映射地址）；TRACE 输出完整原始十六进制报文，不做重复。
- Q: 轮转文件名中的当天序号 N 采用哪种格式？ → A: 不补零，按 `.1`、`.2`、`.10` 递增。
- Q: 现有的 `Request from {地址} ({字节数} bytes)` DEBUG 行与新接收摘要如何共存？ → A: 保留原行，并新增接收摘要与响应摘要。
- Q: DEBUG 摘要与 TRACE 原始字节的日志行应采用哪种标签方案？ → A: 两级均沿用 `Received:` / `Response:` 标签，由日志级别和内容区分。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 通过命令行开启 TRACE 日志 (Priority: P1)

运维或开发人员排查网络问题时，需要在命令行启动服务时直接开启最高详细度的日志，而不必修改配置文件。开启后，每条请求的原始接收报文和响应报文都会以十六进制字节形式记录，便于与抓包结果逐字节比对。

**Why this priority**: 原始报文是定位协议兼容性问题最直接的证据。没有命令行开关时，用户必须编辑配置文件，且默认级别下看不到这些内容，排查效率低。

**Independent Test**: 以 `--trace` 参数启动服务，发送一次 Binding 请求，确认日志中出现该请求的原始字节和响应的原始字节；不使用该参数时确认这些原始字节不会出现。

**Acceptance Scenarios**:

1. **Given** 服务尚未启动，**When** 使用 `--trace` 参数启动并收到一个合法 Binding 请求，**Then** 日志中记录该请求的原始报文字节和对应响应的原始报文字节
2. **Given** 服务以 `--trace` 启动，**When** 查看同一请求的其他日志，**Then** 除原始报文外仍能看到全部 DEBUG 及更高级别日志（TRACE 是更详细的级别，包含 DEBUG 内容）
3. **Given** 服务仅以 `--debug` 启动，**When** 收到请求，**Then** 日志中不出现原始报文十六进制内容

---

### User Story 2 - DEBUG 级别展示可读的报文内容 (Priority: P2)

开发人员在调试协议交互时，希望在不开启 TRACE 的情况下就能看懂请求和响应的语义内容，而不必手动解码十六进制字节。DEBUG 日志应给出接收消息和响应消息的结构化摘要（消息类型、事务 ID、属性类型及可解析的属性值）。

**Why this priority**: 大多数日常排障只需要知道"收到什么请求、回了什么地址"，可读摘要比原始字节更有用；把高噪声的原始字节留在 TRACE，可避免 DEBUG 日志过于冗长。

**Independent Test**: 以 `--debug` 启动服务并发送一次 Binding 请求，确认日志中包含接收消息的类型、事务 ID、属性信息，以及响应中的映射地址信息，同时不包含原始十六进制字节。

**Acceptance Scenarios**:

1. **Given** 服务以 `--debug` 启动，**When** 收到一个合法 Binding 请求，**Then** 记录一条接收消息摘要，包含消息类型、事务 ID 和请求属性信息
2. **Given** 服务以 `--debug` 启动并成功响应，**When** 查看日志，**Then** 记录一条响应消息摘要，包含响应类型、事务 ID 和响应的 XOR-MAPPED-ADDRESS 等属性值
3. **Given** 请求中包含无法识别的属性，**When** 服务记录 DEBUG 摘要，**Then** 未知属性以类型码和长度呈现，日志记录过程不报错且不影响正常响应
4. **Given** 收到无法解析的报文，**When** 服务记录日志，**Then** 以 DEBUG 级别记录"无效请求"及来源地址，并保持服务继续运行

---

### User Story 3 - 轮转日志文件名包含日期与序号 (Priority: P3)

运维人员收集和归档日志时，需要仅凭文件名就能判断日志所属日期及其当天内的先后顺序。轮转后的文件应始终命名为"当天日期.序号"的形式，序号从 1 开始递增，避免同一天多次轮转产生无序号或覆盖的情况。

**Why this priority**: 命名规范化提升日志归档与检索效率，但不影响服务运行和日志内容本身，因此优先级低于日志级别调整。

**Independent Test**: 触发一次大小轮转或跨天轮转后检查日志目录，确认轮转文件名符合 `{前缀}.log.{YYYY-MM-DD}.{N}`，且同一天内 N 依次递增。

**Acceptance Scenarios**:

1. **Given** 服务运行中触发大小轮转，**When** 检查日志目录，**Then** 存在名称为 `{前缀}.log.{当天日期}.1` 的轮转文件
2. **Given** 当天已存在 `{前缀}.log.{当天日期}.1`，**When** 再次触发轮转，**Then** 新文件命名为 `{前缀}.log.{当天日期}.2`，不覆盖已有文件
3. **Given** 服务跨过午夜继续运行并触发轮转，**When** 检查日志目录，**Then** 新一天的文件序号从 1 开始
4. **Given** 轮转文件数量超过保留上限，**When** 执行清理，**Then** 仍按既有保留策略删除最旧文件，新增命名规则不影响清理行为

---

### Edge Cases

- 同时指定 `--debug` 与 `--trace` 时，以更高详细度的 `--trace` 为准
- 配置文件中的级别为 `trace` 且命令行未指定级别时，按配置的 trace 级别运行
- 收到空报文、过短报文或魔数不匹配的报文时，原始字节（TRACE）仍应记录，DEBUG 记录无效请求，服务不得中断
- 同一请求的 DEBUG 摘要需包含事务 ID，确保并发请求的日志可区分（并发日志行不保证严格先后顺序）
- 跨天判断以本机本地时间为准
- 轮转序号仅用于区分同一天内的文件，不改变现有保留天数/文件数策略

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 命令行 MUST 提供 `--trace` 参数，用于将日志级别设置为 TRACE
- **FR-002**: `--trace` MUST 覆盖配置文件中的日志级别，且优先于 `--debug`
- **FR-003**: `--debug` MUST 继续将日志级别设置为 DEBUG，其行为与现有版本兼容
- **FR-004**: 在 TRACE 级别下，系统 MUST 记录每个收到的报文和每个发出的响应的完整原始字节内容
- **FR-005**: 原始报文日志 MUST 仅在 TRACE 级别输出，在 DEBUG 及更低详细度下 MUST NOT 出现
- **FR-006**: 在 DEBUG 级别下，系统 MUST 记录接收消息的可读摘要，至少包含消息类型、事务 ID 及属性描述
- **FR-007**: 在 DEBUG 级别下，系统 MUST 记录响应消息的可读摘要，至少包含消息类型、事务 ID 及响应属性（如映射地址）
- **FR-008**: 无法解析的请求 MUST 以 DEBUG 级别记录来源地址，并继续计入现有错误统计，不影响服务继续运行
- **FR-009**: 所有日志（控制台与文件）MUST 保留毫秒级时间戳
- **FR-010**: 日志轮转文件名 MUST 采用 `{前缀}.log.{YYYY-MM-DD}.{N}` 格式，其中 N 为当天从 1 开始的递增序号且不补零
- **FR-011**: 轮转 MUST NOT 覆盖已存在的轮转文件；序号冲突时 MUST 递增直到找到未使用的名称
- **FR-012**: 默认日志级别 MUST 保持为 INFO，未指定任何级别参数时行为不变
- **FR-013**: 日志级别名称 `trace` MUST 可通过配置文件设置，与命令行开关效果一致
- **FR-014**: 现有的 `Request from {地址} ({字节数} bytes)` DEBUG 日志行 MUST 保留，与新增的接收摘要、响应摘要并存
- **FR-015**: DEBUG 摘要与 TRACE 原始字节 MUST 统一使用 `Received:` / `Response:` 标签，由日志级别和内容区分两者

### Key Entities

- **日志记录**: 一条输出，包含毫秒时间戳、级别（TRACE/DEBUG/INFO/WARN/ERROR）和消息内容
- **消息摘要**: 请求或响应的可读描述，包含消息类型、事务 ID、属性类型及可解析属性值
- **原始报文**: 请求或响应的完整字节序列，以十六进制形式呈现
- **轮转文件**: 日志达到大小上限或跨天时生成的历史文件，名称由前缀、日期和当天序号组成

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 使用 `--trace` 启动后发送一次请求，100% 的请求与响应均能在日志中找到对应的原始字节记录
- **SC-002**: 仅使用 `--debug` 时，原始字节日志出现次数为 0，同时每个成功请求都有接收摘要和响应摘要各 1 条
- **SC-003**: 同一天内连续触发 3 次轮转，生成的 3 个文件名序号分别为 1、2、3，且无文件被覆盖
- **SC-004**: 未指定级别参数启动时，INFO 及更高级别日志行为与调整前完全一致，无需修改现有部署配置
- **SC-005**: 运维人员无需额外解码工具即可从 DEBUG 日志中直接读出请求类型、事务 ID 和响应映射地址

## Assumptions

- TRACE 日志面向故障排查，日志量显著高于 DEBUG，不设为默认级别
- 原始报文沿用现有十六进制字节列表的可视化形式（如 `[00, 01, ...]`），便于与抓包工具比对
- 消息摘要基于现有协议解析能力输出；对暂不支持解析的属性，展示类型码与长度即可
- 轮转序号在每天首次轮转时从 1 开始，跨天后重新计数；保留策略（保留天数/文件数）维持现状
- `--trace` 意味着包含 DEBUG 内容（级别过滤为包含关系），不需要用户同时指定两个参数
- 本特性不改变日志输出目标（控制台/文件）的现有配置项与默认值
- 现有毫秒时间戳实现已满足 FR-009，本特性只需保证新日志沿用该格式
